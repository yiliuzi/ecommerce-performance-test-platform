# 电商接口性能测试计划

## 1. 测试目的

验证电商接口服务在不同并发负载下的性能表现，识别系统容量边界、响应时间变化、错误率以及数据库连接池瓶颈，为服务优化和容量规划提供依据。

## 2. 测试范围

### 2.1 被测接口

| 接口 | 方法 | 说明 |
|---|---|---|
| `/health` | GET | 服务健康检查 |
| `/api/products` | GET | 查询商品列表 |
| `/api/orders/{order_id}` | GET | 查询订单详情 |
| `/api/orders` | POST | 创建订单 |

### 2.2 不在测试范围内

- 前端页面性能
- 公网网络延迟
- 多节点分布式部署
- 生产环境数据库
- 第三方接口性能

## 3. 测试环境

| 项目 | 配置 |
|---|---|
| 操作系统 | Windows |
| Python | 3.13.7 |
| 压测工具 | Locust 2.46.5 |
| API 框架 | FastAPI |
| 数据库 | MySQL 8.0 |
| ORM | SQLAlchemy 2.x |
| 指标采集 | Prometheus |
| 可视化 | Grafana |
| API 地址 | `http://127.0.0.1:8000` |
| Locust 地址 | `http://127.0.0.1:8089` |
| Prometheus 地址 | `http://127.0.0.1:9090` |
| Grafana地址 | `http://127.0.0.1:3000` |

## 4. 测试数据

- 使用独立测试数据库 `ecommerce_test`。
- 使用有效的测试用户和商品数据。
- 订单创建场景记录本次测试创建的订单 ID。
- 测试结束后只删除本次测试生成的数据。
- 不删除数据库中原有订单和商品数据。

## 5. 负载模型

### 5.1 基准测试

- 并发用户：10
- 启动速率：2 用户/秒
- 持续时间：1 分钟
- 目标：获得低负载性能基线

### 5.2 阶梯负载测试

- 并发用户逐步增加至100
- 观察每个负载阶段的 RPS、P95、P99 和失败率
- 目标：识别响应时间明显上升的性能拐点

### 5.3 混合业务测试

建议业务比例：

| 业务操作 | 比例 |
|---|---:|
| 查询商品列表 | 80% |
| 查询订单详情 | 15% |
| 创建订单 | 5% |

目标：模拟读多写少的电商接口使用场景。

### 5.4 峰值测试

- 峰值并发用户：300
- 快速增加负载
- 目标：验证系统过载表现并定位资源瓶颈

### 5.5 稳定性测试

- 并发用户：100
- 启动速率：10 用户/秒
- 持续时间：5分钟
- 目标：检查持续负载下的性能波动和错误累积

## 6. 性能指标

测试期间采集以下指标：

- 总请求数
- 每秒请求数（RPS）
- 平均响应时间
- P50、P95和P99响应时间
- 最大响应时间
- 请求失败数和失败率
- HTTP 5xx错误率
- API进程内存占用
- 数据库连接池超时异常

## 7. 验收标准

### 7.1 100用户稳定负载

| 指标 | 验收标准 |
|---|---:|
| 请求失败率 | `0%` |
| P95响应时间 | `≤ 500 ms` |
| P99响应时间 | `≤ 1,000 ms` |
| 平均RPS | `≥ 80` |
| 服务可用性 | 测试期间无崩溃 |

### 7.2 峰值负载

峰值测试用于发现系统容量边界，不将“全部通过”作为唯一目标。需要满足：

- 服务在过载后能够恢复。
- 错误可以被日志和监控捕获。
- 能够定位主要性能瓶颈。
- 测试过程中无不可恢复的数据损坏。

## 8. 监控方案

Prometheus每5秒采集一次FastAPI `/metrics` 指标。

Grafana Dashboard展示：

- 实时请求速率
- HTTP 5xx失败率
- P95响应时间
- 各接口请求速率
- 平均响应时间
- API进程内存占用

## 9. 测试执行流程

1. 启动MySQL服务。
2. 启动FastAPI服务。
3. 检查 `/health` 和 `/metrics`。
4. 检查Prometheus Target为 `UP`。
5. 打开Grafana Dashboard。
6. 执行Locust测试。
7. 保存Locust CSV或HTML报告。
8. 记录Grafana监控结果。
9. 清理本次测试创建的订单数据。
10. 编写性能测试报告。

## 10. 风险与控制措施

| 风险 | 控制措施 |
|---|---|
| 压测数据污染数据库 | 单独记录并清理测试订单 |
| 服务未启动导致全部失败 | 压测前检查 `/health` |
| 端口被占用 | 启动前检查8000、8089、9090和3000端口 |
| 数据库连接池耗尽 | 监控异常日志并记录连接池参数 |
| 本机资源影响结果 | 测试期间关闭不必要程序 |
| 短时间测试存在波动 | 同一场景重复执行并比较结果 |
